How I Run Local LLMs for Coding (and Why the Quant Matters)

AI;DR — This post was written with AI assistance from my own local model, then edited by me. The setup, tests, and numbers are all real.

Here is the short version: I run a coding assistant entirely on my own hardware — a single RTX 3090 Ti with 24GB of VRAM, serving a 27B model to OpenCode over the LAN. No API bills, no data leaving the house. This post is about the two things that actually bit me: the quantization type silently corrupting output, and a single missing sampler flag causing repetition loops. Both had non-obvious fixes.

I have written before about keeping things local — the Rust proxy, the self-hosted everything. Local LLMs are the same instinct. If the model runs on my desk, I control it, and I can leave it running.

Let’s talk about how I got here.

I did not land on the current setup on day one. It took a couple of months of swapping models and tuning knobs, and most of the interesting lessons came from the dead ends.

I started with a Claude-distilled reasoning model — a Qwen3.6-35B-A3B distilled from Claude 4.7 Opus. It was fine, but it refused things a coding assistant should not refuse, so I moved to an uncensored variant, and then to a cleaner Wasserstein-abliterated build, which is still my fast fallback at about 174 tokens per second.

The turning point was understanding Mixture-of-Experts versus dense models. Those 35B-A3B models are Mixture-of-Experts: 35 billion total parameters but only about 3 billion active per token, so they are fast. I tested a true dense 27 billion parameter model alongside them. The dense model was measurably smarter on benchmarks — but about three and a half times slower because it activates roughly nine times more parameters per token. For an interactive coding agent, speed is a feature, so the fast model usually wins. The exception is when accuracy really matters, and that is where I landed on a dense 27B coder fine-tune as the daily driver, keeping the fast Mixture-of-Experts model around for when I want throughput.

There were two rabbit holes worth exploring.

First, should I switch off llama.cpp to vLLM? vLLM has better speculative decoding and concurrency. But on my RTX 3090 Ti — an Ampere card — the FP8 weight path that makes long context cheap is not supported; it needs Ada or Hopper architecture. Switching would have crushed my context window from 200K down to 32 to 64K. Not worth it. Long context matters more to me than raw latency on this hardware, so I stayed on llama.cpp.

Second, speculative decoding. This is the trick that gets me around 70 tokens per second on a dense 27B model. The model drafts several tokens ahead and the main pass verifies them in one shot. It was fiddly to get working — most Qwen GGUFs ship their MTP heads for vLLM only, not llama.cpp — so finding a build with a working MTP sibling file was half the battle.

I also spent an afternoon overclocking the VRAM using LACT, the Wayland-friendly NVIDIA tool, and measured a whole two percent speedup. That tiny number was actually useful data: it proved this workload is not purely memory-bandwidth bound, so there was no point chasing more.

If there is one meta-lesson from all of that: measure on your own box. Nearly every best model or best setting claim I read turned out to be conditional on hardware I do not have.

Now, let’s look at the setup.

The rig is a Pop!_OS box with an RTX 3090 Ti, which has 24GB of VRAM and uses Ampere architecture. It runs llama.cpp as a systemd service, exposing an OpenAI-compatible API on port 8080. My editor, OpenCode, points a provider at that local address and never knows the difference.

The model is a 27B Qwen3.8 coder variant, quantized to Q4_K_M, which takes up about 16GB on disk. That leaves just enough VRAM for a 200K token context window with a q4_0 KV cache and MTP speculative decoding turned on. It runs around 70 tokens per second. On a coding agent that fires a lot of tool calls, that is plenty.

Here is the actual command, pulled straight from the systemd unit that runs it. You can find the exact code block in the blog post if you want to copy it, but I will walk you through what every one of those flags is doing, because each one matters.

First, the model path points to the GGUF model file on disk, specifically Jackrong’s Q4_K_M quantization.

Second, the context window is set to 200,000 tokens. This is the ceiling for the prompt plus tool output plus the reply combined, and it is the number everything else below is tuned around to make it fit in 24GB of VRAM.

Third, parallelism is set to one. I’m the only client, OpenCode over the LAN, so reserving KV cache for concurrent requests I will never make would just waste VRAM I need for context.

Fourth, the number of GPU layers is set to 99. This is the one that matters most. It offloads every layer to the GPU. Get this wrong and llama.cpp falls back to CPU for the rest — the difference between about 170 tokens per second and two tokens per second.

Fifth, the cache types for keys and values are set to q4_0. This quantizes the KV cache itself, not just the model weights, down to 4-bit. This is the flag that actually makes a 200K context window possible at all; at full-precision KV it would run out of VRAM long before 200K.

Sixth, flash attention is turned on. This uses the fused flash-attention kernel instead of the naive implementation. It’s faster, lower memory, and has no downside on Ampere.

Seventh, no context shift is enabled. This turns off llama.cpp’s default behavior of silently sliding old tokens out of the context window once you hit the limit. For a coding agent that depends on everything it has read and decided so far, I want a hard error at 200K, not a session that quietly forgets its first half.

Eighth, the cache RAM is set to 32768, and the context checkpoints are set to 8. These two work together. llama.cpp can checkpoint prompt-cache state to host RAM so a long agentic session doesn’t have to re-process the entire prompt on every turn. The first flag caps that at 32GB of RAM, and the second flag is how many checkpoint slots it keeps around.

Ninth, the Jinja flag is set. This uses the chat template baked into the GGUF’s metadata instead of a hardcoded one. It is needed for tool-calling to format correctly.

Tenth, the spec type is set to draft-mtp, and the max draft tokens is set to 4. This turns on speculative decoding using the model’s own Multi-Token Prediction head as the draft model, drafting up to 4 tokens ahead per step. This is what gets a dense 27B model to about 70 tokens per second instead of 20 to 25.

Eleventh, reasoning is turned off. Qwen3.8 defaults to an aggressive thinking mode that burns tokens overthinking simple requests. A coding agent just needs the answer.

Twelfth, the temperature is set to 0.7, top-p is 0.8, top-k is 20, and min-p is 0. These are the sampler settings straight from Qwen’s own model card for non-thinking or instruct mode.

Thirteenth, the presence penalty is set to 1.0. This is the repetition fix from the next section. It penalizes tokens that have already shown up, so long sessions can’t loop forever.

Fourteenth, the alias is set to Qwen3.8-27B. This is the model name the OpenAI-compatible models endpoint reports, so OpenCode’s model picker shows something readable instead of the raw GGUF filename.

Fifteenth, the host is set to 0.0.0.0 and the port is 8080. This binds every interface, not just localhost, so other machines on the LAN, like my editor, can reach it.

Now, let’s discuss the issue where the quant type quietly broke things.

When Unsloth shipped their Dynamic 3.0 quants for Qwen3.8, the pitch was great: more accuracy at the same file size. So I downloaded their IQ4_XS build and tested it.

It produced garbage. Not random garbage — subtle garbage. My username came out with an extra 's'. Paths came back with a Cyrillic 'e' swapped in for the Latin 'e'. "MindTouch" became "MMindTouch." This is the kind of corruption you would miss on a quick glance and then spend an hour debugging in a generated script.

The isolation test told the story: run it CPU-only and it was perfect. Run any part of it on the GPU and it corrupted. That pointed straight at a CUDA kernel bug for that model’s linear-attention layers on Ampere cards — not something I could fix.

Here is the part that took a second round to figure out: it was the quant type, not the build. IQ4_XS is an "i-quant." When I tested a Q4_K_M "k-quant" of the same model, on the same GPU, it ran completely clean. Same 27B model, same 4-bit target, wildly different result — because the i-quant path hit the broken kernel and the k-quant path did not.

The lesson: on an Ampere GPU, stick to k-quants like Q4_K_M or Q5_K_M. The i-quants squeeze into less VRAM, which is tempting, but they lean on kernels that are not always solid. I verify every new model with a dumb little test now — ask it to echo an exact path ten times and check the characters are right before I trust it with real work.

There was one more flag that fixed my looping problem.

The other issue was repetition. In long agentic sessions, the model would occasionally get stuck repeating itself. Short prompts were fine; long ones would eventually self-reinforce a pattern with nothing to break it.

When I checked the live server config, the cause was plain: I had no repetition control turned on at all. No presence penalty, no DRY sampler. With zero guard, short generations rarely hit a repeating loop, but a long session would find one and never climb out.

Unsloth’s model card recommends a presence penalty of 1.5 for this model in non-thinking mode. Before changing my daily driver, I tested it — five loop-prone prompt types, like long enumerations, repetitive code, and the classic "continue this list" trap, at 1200 tokens each, across presence penalty values of 0.6, 1.0, and 1.5.

The results were clear enough to act on.

At 0.6, four out of five tests were clean. Only the nastiest "keep going without restarting" prompt degraded.

At 1.0, all five were clean, balanced, and had no side effects.

At 1.5, all five were also clean, but it started stopping early and wandering off-format on structured tasks.

Speed was identical across all three, so there was no performance cost either way. I landed on 1.0, not the recommended 1.5 — it fixed the failure without the format-drift.

Unsloth’s number was a good starting point, but the right value for my workload was milder. Test it against the thing you actually do, not the thing the docs assume you do.

Would I do it again? Yes. Once it is dialed in, a local coding model is genuinely useful and costs nothing per token. But it is not plug-and-play. The two things that cost me the most time were not "which model is best" — they were the quant type interacting badly with my specific GPU, and a sampler default I never set.

Both are the kind of thing you only find by testing on your own hardware with your own prompts. Which, honestly, is half the fun.
