ASP.NET XSS Protection

Securing an ASP.NET Web API for PCI application tests is no trivial matter. It can take weeks of planning and analyzing the app. After reviewing OWASP and other related cross-site scripting sites, the web.config was the first to be updated to prevent against attacks, specifically Man-in-the-Middle and cross-site scripting.

To give you the gist of what is happening, we are removing standard headers like Server, X-Powered-By, and various protection headers that might be set by default. We are then adding back specific, stricter versions of those headers. This includes setting X-Frame-Options to Deny, enabling XSS protection in block mode, setting Content-Type-Options to nosniff, and configuring cache control to ensure data isn't stored. We are also setting the Expires header to a date in the past to prevent caching, and defining a Content Security Policy that restricts where resources can come from, allowing only inline scripts and self-hosted resources, with exceptions for fonts and images from HTTPS sources.

The Content Security Policy was the only one considered less secure due to outside JavaScript and CSS resources the app used, such as Google Analytics and Bootstrap.

Let's look at additional protection. First, you should apply the AntiXSS attribute from the ASP.NET Web API AntiXSS Attribute project. You can find that project on Bitbucket. Second, use a Website Application Firewall for your apps. Examples of these include Amazon WAF, ModSecurity, IronBee, NAXSI, WebKnight, and Shadow Daemon.

Regarding tools, look for open source tools that are commonly used for penetration testing. These tools gave some pretty good insight on where the app needed securing. Specifically, you should check out Nikto2, SQLMap, and OWASP ZAP.

Finally, here are the key takeaways. First, don't rely on just one layer of protection. Second, use established frameworks. Third, use the same tools as the pen testers.
