I wrote the first draft of this post, used AI to help me edit and rewrite it, and then I made the final pass myself.

Here is the short version. Out of 8,809 Sony photos in my Immich library, only one burst was steady enough to merge cleanly. That changed what the app had to be. Burst Super-Res is free and open source under the MIT license. It runs offline on macOS, Windows, and Linux. You can find the download link on the blog post if you want it.

There is also a web version that runs in your browser, but the desktop app is preferred because it is optimized for that environment. If you are following the Sony A6000 or A6400 series, this is the final part. You can find links to the modernization guides, the hack posts, the Raspberry Pi tethering post, and the research resources on the main blog page.

Let's look at the image at the top of the post. It shows a real eight-shot burst from a Sony A6000 taken of a canyon. There is a before-and-after slider over the cliffs. On the left side of the slider, you see one photo upscaled by two times. On the right side, you see the mean of all eight photos merged together.

So, what is this thing? You drop in a burst of photos of the same still scene. The app lines them up to a fraction of a pixel and merges them. The result has twice the width and height. Four photos that are 6,000 by 4,000 pixels become one image that is 12,000 by 8,000 pixels. It reads JPEG, PNG, and Sony ARW RAW files, and it keeps your EXIF data. A split slider shows you what the merge did.

There is no AI in the processing. Every output pixel comes from pixels the camera recorded, averaged after alignment. AI upscalers invent detail that looks plausible. This only uses detail that is really there. That is also why the gain is small. Expect less noise and cleaner fine edges. Do not expect four times the detail. That is why the app never shows a megapixel number. On simulated bursts with a known answer, the gain over one upscaled photo was between plus zero point seven and plus one point three decibels in PSNR. It is real, but it is modest.

Why build it? Part one of the Sony series had a super-resolution trick. You shoot four photos, upscale each by 200 percent, align them, blend two at 50 percent, then blend the two results. On paper, that is 97.2 megapixels. In practice, it looked more like 48.6 megapixels. Why not just use the script? Because nobody wants to set up a Python environment to merge four photos. A download is easier.

I set some rules before any code was written. First, no AI in the processing. Every pixel has to come from the photos. Second, measure on real data and publish the numbers, including where a feature hurts. Third, cross-platform without Electron. The app uses TinyJS, which runs the UI in the operating system webview. The Linux build is about 10 megabytes.

Research drove the changes below. Each idea got measured against a benchmark before it went in.

Here is the benchmark. A real burst has no true high-resolution image to score against. So I made one. Take a real 24-megapixel A6000 or A6400 photo as the answer. Shift copies by random sub-pixel amounts. Downsample them by two times, the way a sensor pixel averages light. Add noise and save as JPEG. Then merge them back and score against the original. The baseline is the same reference photo upscaled two times with Lanczos-3, so both sides have the same output size.

The first attempt at the benchmark was wrong, but nothing looked off. The harness decoded with a library that truncates instead of rounding. That shifted every pixel by minus 0.53 levels per round trip and skewed every score. Switching to a different decoder fixed it. Every number in this post comes from that fixed harness. You can run it yourself on your own photos using the command in the blog post.

The original method is just a mean. The pairwise 50/50 blend from Part 1 is a plain average with extra rounding. For four photos, you blend A plus B, blend C plus D, then blend those two. Every photo ends up at 25 percent. That is a mean, rounded to 8 bits after each stage. For three photos, it is worse because the weights come out 25, 25, and 50.

The default became a per-pixel mean or median over all aligned photos. The weights are exact for any count. Pairwise is still in the app if you want to compare.

The bigger change was alignment. The Python version matched SIFT features and fit a homography. Version 0.1 uses sub-pixel registration instead. It builds an image pyramid, runs the Lucas-Kanade method on tiles, then fits an affine warp through the tile shifts. On simulated bursts, it lands within 0.03 pixels, even when rotated by 0.5 degrees.

Shift-and-add was tried and dropped. It places every input pixel at its exact sub-pixel spot on the two-times grid. On synthetic test patterns with heavy aliasing, it beat the mean by 1.0 to 1.7 decibels. On real photos, it tied the mean. On a detailed canyon crop, it was 0.2 to 0.5 decibels worse. So it went out.

You need a tripod, do not forget it. Version 0.1 only had simulated bursts to show. So I went looking for real ones in Immich. It has 1,880 Sony photos from the A6400 and 6,929 from the A6000. Shots seconds apart with the same settings gave 732 burst candidates. I ran the app's own alignment over 348 of them.

302 were handheld and more than 10 pixels off. One was steady. It is a 13-shot A6000 canyon burst, taken at 20 millimeters, f/11, and ISO 100. That is the photo at the top of this post. Even that one had three frames that did not line up well enough for version 0.1.

Here is an image showing one photo upscaled two times next to five real photos merged. In the crop, you can see less noise and fewer JPEG block edges in the merged version.

That is 302 of 348 bursts shot handheld. That is from someone who wrote a guide on this! A tool that only works on a tripod is a tool for almost nobody.

Borrowing from tools that already solved this. Here is how other tools handle it. These got checked before building more.

DeepSkyStacker scores every frame and stacks only the best ones. Version 0.1 warned about bad frames and made you untick them by hand.

Lightroom uses a backslash key to toggle before-and-after and the letter Y for side-by-side. Photographers already know those keys.

Topaz Gigapixel compares results with one shared navigator.

Sony's own pixel-shift workflow gives you the shooting rules and the wait time up front.

Google's Handheld Multi-Frame Super-Resolution paper is behind Pixel's Super Res Zoom. It treats hand tremor as the source of the useful sub-pixel shifts. The catch is that each region needs its own alignment.

That last one changed the plan. Version 0.2 added local alignment. When the global fit is worse than 0.1 pixel, a grid of 64-pixel cells gets measured and corrected on top of it. Take a real handheld pair where the camera moved 52 pixels. The near cactus and the far hills shifted by different amounts. The error went from 4.36 pixels, which looked like a doubled cactus, to 0.06 pixels. All eight canyon frames came in at 0.22 pixels or better.

Here is an image showing the same handheld pair merged with one shift and rotation, and with local alignment. On the left, you see one shift and rotation for the whole photo, which was 4.36 pixels off. On the right, you see local alignment, which is only 0.06 pixels off.

Version 0.2 also added the Lightroom keys and a Good, Soft, or Too Far Off badge per photo. Bad frames get unticked for you. Any 64-pixel area where something moved, like water, leaves, or people, is left out of that photo so it does not ghost. When a burst is too far gone, the app says so.

Here is an image of the app warning that a soft photo is used and part of it was left out. It shows two handheld shots four seconds apart with about 370 pixels of movement. The app uses the photo but says it is soft.

What the papers said, and what measured better. Next came the research on alignment and stacking. I measured the cheap ideas before adopting any of them.

Here are the numbers for a four-frame simulated burst.
For the A6000 canyon photo: One photo upscaled two times scored 33.51 decibels. The mean merge scored 34.58 decibels. Mean plus gentle deblur scored 35.54 decibels. Sigma-clipped mean scored between 34.48 and 34.54 decibels. Deblur on one photo alone scored 32.69 decibels.
For the A6400 photo, which was mostly out of focus: One photo upscaled two times scored 38.60 decibels. The mean merge scored 39.84 decibels. Mean plus gentle deblur scored 39.79 decibels. Sigma-clipped mean scored between 39.77 and 39.82 decibels. Deblur on one photo alone scored 37.56 decibels.

Deblurring only helps after the merge. On a single photo, it made things worse. That matches the two-step approach in the paper Fast and Robust Multiframe Super Resolution. Stacking lowers the noise enough for deconvolution to work. Sigma clipping is the astro stacking staple from the Siril software. It did not help here because the per-area masking already takes care of moving things.

That turned into three features in version 0.3.

First, sharpening after the merge. It is a gentle Richardson-Lucy deconvolution. Clarkvision compares it against unsharp masking on real photos. Auto leaves one photo out of the merge and picks the amount that predicts that photo best. It is off by default for camera JPEGs. They are already sharpened in camera, and Auto measured up to 0.9 decibels worse on those.

Second, brightness matching. Exposure flicker gets measured per photo and color, then evened out. With plus or minus 5 percent simulated flicker, it recovered the true gains to within 0.001.

Third, RAW, specifically Sony ARW. The point is that a camera JPEG already threw away the fine aliasing detail super-resolution needs. With six or more ARW files, every output pixel is built from the raw sensor samples of all the photos. There is no demosaicing in between. The ARW decoder is written from scratch in JavaScript. It matches LibRaw on all 24.2 million samples of a real A6000 file. In simulations, RAW scored 0.9 to 2.5 decibels better than the same burst as JPEGs.

Here is an image showing six camera-style JPEGs merged next to the same six RAW files merged from sensor samples. It shows a simulated six-photo burst merged as camera JPEGs versus merged from RAW sensor samples.

I have one real ARW to test with and no real RAW burst. So every RAW quality number above is from simulated bursts.

Deep-learning burst super-resolution tops the benchmarks. You can look at the Deep Burst Super-Resolution paper and the Burstormer paper. It also invents detail and needs a big model or a GPU, which breaks the first rule. If you want more on the classical side, the IPOL re-implementation of Google's method walks through every step with its own measurements. And the CANDID paper covers optical-flow alignment for scenes with a lot of depth.

Where the pixel work runs. TinyJS apps have two halves. There is a backend and the OS webview. The backend runs QuickJS with no JIT. A tight loop over 96 megabytes of pixels per photo is exactly where a JIT matters. So all the math runs in the page in Web Workers. The backend only writes the output file.

One gotcha. Chromium, which WebView2 uses, blocks workers loaded from file URLs. The worker gets built from function source as a Blob URL instead. The output goes back to the backend in 3-megabyte base64 chunks because the bridge is text.

The latest change spreads alignment and merging over a pool of helper workers. Four real 24-megapixel JPEGs went from 31.5 seconds to 14.1 seconds on a 24-core machine. The output matches the single-threaded version pixel for pixel. That shipped in version 0.4.0 along with EXIF in PNG output.

Shipping it. GitHub Actions builds every platform from a tag, plus Linux AppImages. Every release file has a GitHub build attestation. The checksum file and AppImages are GPG-signed. You can verify your download using the commands found in the blog post code block.

What is left? It has only been tested on Linux. The macOS, Windows, and Linux ARM64 builds come out of CI and nobody has launched them yet. Try one and open an issue if it breaks.
