Quick note before we dive in: this post was written with AI assistance from my own local model, and then I edited it myself. The setup, the tests, and all the numbers I’m about to share are real.

Here is the short version. I run a coding assistant entirely on my own hardware. It is a single RTX 3090 Ti with 24 gigabytes of video memory, serving a 27 billion parameter model to my editor over my local network. There are no API bills, and no data leaves the house. This post is really about two specific things that bit me: first, a quantization type that silently corrupted the output, and second, a single missing sampler flag that caused the model to get stuck in repetition loops. Both had fixes that were not obvious at first.

I have written before about keeping things local. I talked about building a custom HTTP proxy in Rust, and self-hosting pretty much everything else. Local large language models are the same instinct. If the model runs on my desk, I control it, and I can leave it running indefinitely.

How I Got Here

I did not land on my current setup on day one. It took a couple of months of swapping models and tuning settings, and most of the interesting lessons came from the dead ends.

I started with a Claude-distilled reasoning model. It was a Qwen 3.6, 35 billion parameter mixture of experts model, distilled from Claude 4.7 Opus. It was fine, but it refused things that a coding assistant should not refuse. So I moved to an uncensored variant, and then to a cleaner Wasserstein-abliterated build. That one is still my fast fallback, running at about 174 tokens per second.

The turning point was understanding the difference between mixture of experts and dense models. Those 35 billion parameter models are mixtures of experts. They have 35 billion total parameters, but only about 3 billion active per token, which makes them fast. I tested a true dense 27 billion model alongside them. The dense model was measurably smarter on benchmarks, but it was about 3.5 times slower because it activates roughly nine times more parameters per token. For an interactive coding agent, speed is a feature, so the fast model usually wins.

The exception is when accuracy really matters. That is where I landed on a dense 27 billion coder fine-tune as my daily driver. I use Jackrong's Qwopus build, and later a Qwen 3.8 build. I keep the fast mixture of experts model around for when I want higher throughput.

There were two rabbit holes that were worth the time.

First, should I switch off llama.cpp to vLLM? vLLM has better speculative decoding and concurrency. But on my RTX 3090 Ti, which is an Ampere card, the FP8 weight path that makes long context cheap is not supported. It needs Ada or Hopper architecture. Switching would have crushed my context window from 200,000 tokens down to maybe 32,000 or 64,000. That was not worth it. Long context matters more to me than raw latency on this hardware, so I stayed on llama.cpp.

Second, speculative decoding, specifically Multi-Token Prediction. This is the trick that gets me about 70 tokens per second on a dense 27 billion model. The model drafts several tokens ahead, and the main pass verifies them in one shot. It was fiddly to get working. Most Qwen GGUF files ship their MTP heads for vLLM only, not for llama.cpp. So finding a build with a working MTP sibling file was half the battle.

I also spent an afternoon overclocking the video memory. I added 1500 megahertz using a tool called LACT, which is a Wayland-friendly NVIDIA tool. I measured a whole 2 percent speedup. That tiny number was actually useful data. It proved that this workload is not purely memory-bandwidth bound, so there was no point chasing more.

If there is one meta-lesson from all of that, it is this: measure on your own box. Nearly every "best model" or "best setting" claim I read turned out to be conditional on hardware I do not have.

The Setup

The rig is a Pop!_OS box with an RTX 3090 Ti, 24 gigabytes of memory, Ampere architecture. It runs llama.cpp as a systemd service, exposing an OpenAI-compatible API on port 8080. My editor, OpenCode, points a provider at that local address and never knows the difference.

The model is a 27 billion Qwen 3.8 coder variant, quantized to Q4 K M. That takes up about 16 gigabytes on disk. That leaves just enough video memory for a 200,000 token context window with a q4_0 key-value cache and MTP speculative decoding turned on. It runs around 62 tokens per second on the current llama.cpp build. On a coding agent that fires a lot of tool calls, that is plenty.

Here is the actual command I use, pulled straight from the systemd unit that runs it. I have updated this since first publishing, so see the follow-ups below for changes.

The command starts with llama-server. Then I specify the model file at the path models, qwen 3.8, 27b, jackrong, Qwen 3.8, 27B, MTP, Q4 K M, GGUF. The context size is set to 200,000 tokens. Parallelism is set to 1. The number of GPU layers is set to 99, which offloads everything to the GPU. The unbatch size is 2048. The cache type for keys is q4_0, and the cache type for values is q4_0. Flash attention is on. Context shift is turned off. Cache RAM is 32,768 megabytes. Context checkpoints are set to 8. I use Jinja templates with a specific chat template file. The spec type is draft-mtp, with a max draft of 4 tokens. Reasoning is off. The temperature is 0.7, top-p is 0.8, top-k is 20, and min-p is 0. The presence penalty is 1.0, and the dry multiplier is 0.8. The alias is Qwen 3.8, 27B. It hosts on all interfaces on port 8080.

Every one of those flags is doing something specific.

The model path flag points to the GGUF file on disk. This is Jackrong's Q4 K M quant, about 16 gigabytes.

The context flag sets the window to 200,000 tokens. This is the ceiling for prompt plus tool output plus reply combined. It is the number everything else is tuned around to make it fit in 24 gigabytes of video memory.

Parallelism is set to 1, not the default of several. I am the only client, so reserving key-value cache for concurrent requests I will never make would just waste video memory I need for context.

The number of GPU layers flag is set to 99. This is the one that matters most. It offloads every layer to the GPU. If you get this wrong, llama.cpp falls back to CPU for the rest. The difference is between about 170 tokens per second and about 2 tokens per second.

The unbatch size is 2048. This is the physical batch size llama.cpp uses internally for prompt processing. Bumping this from the default 512 sped up prefill noticeably on long agentic prompts. I confirmed this with llama-bench before adopting it.

The cache type flags for keys and values are set to q4_0. This quantizes the key-value cache itself, not just the model weights, down to 4-bit. This is the flag that actually makes a 200,000 token context window possible at all. At full-precision key-value, it would run out of video memory long before 200,000 tokens.

Flash attention is on. This uses the fused flash-attention kernel instead of the naive implementation. It is faster, uses less memory, and has no downside on Ampere cards.

Context shift is turned off. This turns off llama.cpp's default behavior of silently sliding old tokens out of the context window once you hit the limit. For a coding agent that depends on everything it has read and decided so far, I want a hard error at 200,000 tokens, not a session that quietly forgets its first half.

Cache RAM is set to 32,768 megabytes, and context checkpoints are 8. These two work together. llama.cpp can checkpoint prompt-cache state to host RAM so a long agentic session doesn't have to re-process the entire prompt on every turn. The cache RAM flag caps that at 32 gigabytes of RAM, and the checkpoints flag is how many checkpoint slots it keeps around. I have watched this cache absorb a 97,000-token prompt down to 294 tokens of actual reprocessing. It is worth every megabyte of host RAM.

The Jinja flags tell the server to use a real Jinja2 chat template instead of a hardcoded one. I load this from a file I control rather than whatever is baked into the GGUF file. This is needed for tool-calling to format correctly, and it is easier to patch when a model's shipped template has a bug.

The spec type and draft max flags turn on speculative decoding using the model's own Multi-Token Prediction head as the draft model. It drafts up to 4 tokens ahead per step. This is what gets a dense 27 billion model well past what plain autoregressive decoding would manage.

Reasoning is off. Qwen 3.8 defaults to an aggressive "xhigh" thinking mode that burns tokens overthinking simple requests. A coding agent just needs the answer.

The temperature, top-p, top-k, and min-p settings are straight from Qwen's own model card for non-thinking or instruct mode.

The presence penalty is 1.0, and the dry multiplier is 0.8. This is the repetition fix, now in two parts instead of one. More on why in the section below.

The alias flag sets the model name that the OpenAI-compatible models endpoint reports. This allows OpenCode's model picker to show something readable instead of the raw GGUF filename.

Finally, host and port are set to bind every interface on port 8080, not just localhost. This allows other machines on the LAN, like my editor, to reach it.

The Quant Type Quietly Broke Things

When Unsloth shipped their Dynamic 3.0 quants for Qwen 3.8, the pitch was great: more accuracy at the same file size. So I downloaded their IQ4 XS build and tested it.

It produced garbage. Not random garbage, but subtle garbage. My username came out as "spencerkittlesson" with an extra 's'. Paths came back with a Cyrillic 'е' swapped in for the Latin 'e'. "MindTouch" became "MMindTouch". It was the kind of corruption you would miss on a quick glance and then spend an hour debugging in a generated script.

The isolation test told the story. I ran it CPU-only, and it was perfect. I ran any part of it on the GPU, and it corrupted. That pointed straight at a CUDA kernel bug for that model's linear-attention layers on Ampere cards. It was not something I could fix.

Here is the part that took a second round to figure out. It was the quant type, not the build. IQ4 XS is an "i-quant." When I tested a Q4 K M "k-quant" of the same model, on the same GPU, it ran completely clean. Same 27 billion model, same 4-bit target, wildly different result. The i-quant path hit the broken kernel, and the k-quant path did not.

The lesson is this: on an Ampere GPU, stick to k-quants, like Q4 K M or Q5 K M. The i-quants squeeze into less video memory, which is tempting, but they lean on kernels that are not always solid. I verify every new model with a dumb little test now. I ask it to echo an exact path ten times and check the characters are right before I trust it with real work.

One Flag Fixed My Looping Problem

The other issue was repetition. In long agentic sessions, the model would occasionally get stuck repeating itself. Short prompts were fine, but long ones would eventually self-reinforce a pattern with nothing to break it.

When I checked the live server config, the cause was plain. I had no repetition control turned on at all. No presence penalty, no DRY sampler. With zero guard, short generations rarely hit a repeating loop, but a long session would find one and never climb out.

Unsloth's model card recommends a presence penalty of 1.5 for this model in non-thinking mode. Before changing my daily driver, I tested it. I used five loop-prone prompt types, like long enumerations, repetitive code, and the classic "continue this list" trap. I ran them at 1200 tokens each, across presence penalty values of 0.6, 1.0, and 1.5.

The results were clear enough to act on.

At 0.6, four out of five were clean. Only the nastiest "keep going without restarting" prompt degraded.

At 1.0, five out of five were clean, balanced, with no side effects.

At 1.5, also five out of five were clean, but it started stopping early and wandering off-format on structured tasks.

Speed was identical across all three, so there was no performance cost either way. I landed on 1.0, not the recommended 1.5. It fixed the failure without the format-drift.

The command flag is simply: presence penalty 1.0.

Unsloth's number was a good starting point, but the right value for my workload was milder. Test it against the thing you actually do, not the thing the docs assume you do.

Follow-up: Unlocking the 3090 Ti, and a Faster llama.cpp

A while after publishing, I swapped the daily driver to a newer dense Qwen 3.8 build. It is bytkim's Qwen 3.8, 27B, PI, an agentic-coding fine-tune. Unlike the Jackrong model, its MTP head ships as a separate draft GGUF you load with the minus MD flag. So the draft model wants its own slice of video memory. At a context of 200,000, it would not even start. It failed with a CUDA malloc error, out of memory, before the first token.

The fix was three flags that shrink the draft's footprint without touching the main model's context.

First, spec draft N unbatch set to 512. Second, cache type key draft set to q4_0. Third, cache type value draft set to q4_0.

The draft's key-value cache was defaulting to full FP16 while the main model ran at q4_0. Quantizing the draft cache and halving its batch, plus dropping the main unbatch size to 1024, brought a 200,000 window back, with about 1 gigabyte of headroom left on the card. The model reads a roughly 188,000-token prompt without falling over. That is the whole reason I run this thing instead of renting one.

The Thing I Actually Got Nerd-Sniped By: Unlocking the Card

GA102 Ampere cards, like the 3090, 3090 Ti, and 3080, ship with their FP16 or BF16 tensor-core issue rate halved in firmware relative to the pro-grade A-series silicon. Someone reverse-engineered a kernel module that writes the pro speed selectors before the NVIDIA driver binds the card. I installed it.

A raw 8192 cubed GEMM confirmed it worked. BF16 with FP32 accumulate went from the stock roughly 87 teraflops to 142. TF32 went from about 43 to 75. That part worked exactly as advertised.

Here is the catch, and it is a good lesson in not trusting a headline number. It barely helped llama.cpp. For quantized weights, llama.cpp's matrix multiplication path either uses its own INT8 kernels or dequantizes to FP16 and accumulates in FP16. FP16-accumulate math was never throttled on consumer cards, so the unlock has nothing to speed up.

There is an environment variable that switches to the BF16-plus-FP32-accumulate path that the unlock does touch. At a large batch size, it won about 11 percent on prefill. But at the batch size my 200,000 context actually needs, which is an unbatch size of 1024, that gain evaporated, and small prompts got 30 percent slower. For an agent that sends a lot of small follow-up turns, that is a net loss, so I left it off.

What did move the needle was boring: I rebuilt llama.cpp from a months-old checkout to current master. That alone bought 14 to 19 percent faster prefill across every prompt size, from upstream kernel work, not from anything I tuned. The unlock is a neat trick, and the card is genuinely faster at FP32-accumulate math now. It just is not the math this workload leans on. Measure the thing you run, not the benchmark on the box.

Would I Do It Again?

Yes. Once it is dialed in, a local coding model is genuinely useful and costs nothing per token. But it is not plug-and-play. The two things that cost me the most time were not "which model is best." They were the quant type interacting badly with my specific GPU, and a sampler default I never set.

Both are the kind of thing you only find by testing on your own hardware with your own prompts. Which, honestly, is half the fun.
