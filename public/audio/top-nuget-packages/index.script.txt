Here are the top five NuGet packages I consistently use in most of the projects I’m building. I’ll walk you through some examples so you can see how they’re actually used in practice.

First up is FluentValidation. You can install it by using the command "Install-Package FluentValidation." Dealing with user input validation can be quite tedious, but this package makes the process significantly less painful. It allows you to define rules for your data models in a very readable way. For instance, if you have a customer model, you can create a validator class that inherits from AbstractValidator. Inside that, you can set rules like saying the surname must not be empty, or that the forename is required with a specific error message like "Please specify a first name." You can also add conditional logic, such as checking that a discount value isn't zero only if the customer actually has a discount applied. You can even enforce length constraints on things like addresses, requiring them to be between twenty and two hundred and fifty characters long. You can also plug in custom logic for things like validating a postcode format.

Once your validator is set up, using it is straightforward. You create an instance of your customer object and your validator, then you call the Validate method on the validator, passing in the customer. This returns a result object that tells you whether the validation succeeded or failed. If it failed, you can look at a list of specific failure messages to see exactly which rules were violated. If you want to dive deeper into the source code or see more examples, you can find the link on the blog post.

The second package is Microsoft.Extensions.DependencyInjection. You install this with "Install-Package Microsoft.Extensions.DependencyInjection." Dependency injection, also known as inversion of control, is a very popular pattern in software development. Lately, I’ve stuck with the Microsoft version because it integrates nicely with ASP.NET Core and keeps things fairly simple. One of the biggest benefits is that unit testing becomes much easier since you can mock the interfaces.

In a typical setup, you create a service collection where you register your services using their interfaces along with their concrete implementations. For example, you might register a singleton for an interface called IFoo, pointing to a class called Foo. You might also register a scoped service for an interface called IBar, pointing to a class called Bar. After registering these, you build the service provider from that collection. When you need to use one of these services, you create a scope from the provider, and then you can request the specific service instance you need from that scope's provider. This makes your code loosely coupled and easy to test. You can find more details on how to use this effectively via the link in the blog post.

Third is Easy.Common. To get started, just use "Install-Package Easy.Common." Have you ever tried counting the lines of a very large file? If not, you might want to, because it can get complicated quickly if you try to do it manually. This package provides some really useful extensions to handle that. For example, if you have a very large CSV file, you can create a FileInfo object for it, open a read stream, and then simply call a CountLines extension method on that stream. It handles the heavy lifting for you so you don't have to worry about memory issues or parsing the stream manually. Besides counting lines, there are other useful extensions available in this package. You can check out the GitHub reference on the blog post if you want to explore what else it offers.

The fourth entry is a trio of packages: Xunit, Moq, and AutoMoq. To set these up, you would install xunit, then Moq, and finally AutoFixture.AutoMoq. These are essential for testing. Let’s look at a quick example of mocking in action. Imagine you have an asynchronous method that gets a message from a cache. In your test, you first arrange the scenario by creating an expected value, perhaps a random number generated by your fixture. Then you set up your mock to expect that this specific value will be requested. When it is requested, the mock returns a pre-built message object where you’ve explicitly added a header with that UID.

Next, you act by calling the method under test, which in this case is an async method to get the message. Finally, you assert that the result is correct, specifically checking that the header in the returned message matches the expected UID you set up in the arrange phase. This ensures that your dependency is behaving exactly as you expect it to during the test. If you need a refresher on getting started with Xunit or want to learn more about writing unit tests with Moq, there are links in the blog post that guide you through those specific documentation pages.

The fifth and final top pick is Polly. You can install it with "Install-Package Polly." Do you need retry logic? What about exponential backoff? This project solves those problems easily and comes with tons of extensions to tweak the behavior. A common use case is handling transient exceptions, like network blips or temporary service unavailability. You can define a policy that says, "If a TransientException occurs, wait and retry." For example, you could set it to retry three times, waiting one second between each attempt.

When you execute this policy, you wrap your operation in a delegate. In the example, I’m just logging the attempt number and then throwing a transient exception to simulate a failure. The policy catches that, waits, and tries again up to the limit you specified. This makes your applications much more resilient to temporary faults without you having to write all that retry logic yourself. You can find the GitHub repository link on the blog post if you want to see all the different policies you can configure.

Now, while those were the top five, there are quite a few honorable mentions that I also use or recommend. Let’s go through them quickly.

First is LambdaSharp, which helps you deploy to AWS Lambda and manage resources more easily and safely. Second is PubSub, which implements the publish and subscribe pattern for loose coupling. Third is M2MqttDotnetCore, a client for working with MQTT messaging. Fourth is SynthesizerAudio, which is great if you need to synthesize text to speech.

Fifth is Microsoft.OpenApi, which is similar to Swagger but often considered better in certain contexts. Sixth are the IdentityModel token libraries, specifically Microsoft.IdentityModel.Tokens and System.IdentityModel.Tokens.Jwt. These are essential for working with JWTs. I’ll admit the documentation isn’t the easiest to read, but it is crucial for understanding how to use them correctly.

Seventh is Refit, which is a safe, type-safe REST client library. Eighth is S22.Imap.Core, which allows you to interact with email via IMAP; it’s a simple and easy-to-use library for that purpose. Ninth is Microsoft.Extensions.Caching.Memory, which provides a way to handle caching safely in your applications.

Tenth is EmbedIO, a cross-platform server for HTTP and WebSocket connections. And finally, Watson, which is another cross-platform HTTP server that includes attribute routing, making it very developer-friendly.

That covers the top five packages I rely on, along with some other useful tools that have made my life as a .NET developer a lot smoother.
