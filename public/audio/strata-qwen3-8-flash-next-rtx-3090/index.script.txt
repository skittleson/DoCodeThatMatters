Hey there, friend. I’ve been spending some time tinkering with my homelab, specifically trying to run a massive 125-billion parameter model on a single RTX 3090 Ti. This post was written with AI assistance but edited by me, and all the numbers you’re about to hear are straight from my own machine.

Here’s the short version: On my 3090 Ti, a 125-billion parameter model can now read an 86,000-token prompt in just 32 seconds. My older 27-billion parameter model took 83 seconds to do the same thing. In terms of generation speed, the new model hits about 100 tokens per second, whereas the old one managed between 49 and 70. The engine powering this is called Strata, and the model is Qwen 3.8 Flash Next. I’m sharing the research and the exact configuration I ended up with, so you can copy it if you want.

I updated this guide after my first full day of using it for real agent work. The current setup now uses a 200,000-token context window with a conversation cache. I’ll cover what broke, what it cost, and what I learned toward the end. This follows my previous post on how I run local LLMs for coding, where I used a dense Qwen 27-billion model on llama dot cpp. That setup is still on disk and just one command away. I’m giving Strata one week as my daily coding model before making a final decision.

Let’s start with the hardware. My box has an Nvidia GeForce RTX 3090 Ti Founders Edition with 24 gigabytes of VRAM. The driver version is 580 point 173. For the CPU, I have a Ryzen 9 5950X, which supports AVX2 but notably lacks AVX-512. I have 62 gigabytes of DDR4 RAM, split into two 32-gigabyte sticks. The motherboard is a Gigabyte B450 Aorus M, which means the GPU is connected via a PCIe 3.0 x16 slot. Storage is handled by a Samsung 980 Pro 2TB SSD. The operating system is Pop OS 22.04. And critically, I’m on Wi-Fi, which matters a lot when you’re downloading an 82-gigabyte file. My coding agent, OpenCode, runs on my laptop and talks to this box over the local network using a tool called OmniRoute.

Now, let’s talk research. How does a 125-billion parameter model fit into just 24 gigabytes of VRAM? Flash Next is a Mixture-of-Experts model. While it has 125 billion parameters, only about 6 billion are active for any given token. The rest of the model consists of thousands of small experts, and each token only uses a few of them. Strata works by keeping the experts you use most frequently in VRAM. It keeps all of them in system RAM, and the CPU handles the ones the GPU can’t fit. A 29-gigabyte n-gram lookup table stays on the SSD. Llama dot cpp can run this model too, but it places experts on the GPU by layer rather than by usage frequency, which costs significantly more performance.

The best comparison I found comes from Insider LLM. They compared Strata at 78 tokens per second versus llama dot cpp at 18 tokens per second on a 3090 with 64 gigabytes of RAM. When drafting was enabled, Strata reached about 119 tokens per second and read a 32,000-token prompt in about 12 seconds. In their test, 98.7 percent of expert lookups during decoding hit the graphics card. Since that setup is close enough to mine, I stopped looking at other engines.

Next, which model size should you pick? Strata offers four sizes using quants from ISTA-DASLab. Let me read through the options and their memory requirements. First, there is Q2 underscore zero. It needs 37.6 gigabytes of combined RAM and VRAM. It’s the fastest in Strata’s tables. Second is IQ2 underscore XS, which requires 39.2 gigabytes. This is Strata’s general recommendation. Third is IQ3 underscore XXS, needing 47 gigabytes. This is the size Insider LLM benchmarked. Fourth is IQ3 underscore S, which requires 54.8 gigabytes and claims to match the full model on published tests.

I started by downloading Q2 underscore zero but stopped at 20.7 gigabytes. Two things changed my mind. First, part of Q2 underscore zero’s speed comes from an AVX-512 CPU kernel, and my Ryzen 5950X does not have AVX-512. Second, people testing real coding tasks on Reddit rated the 3-bit sizes clearly above the 2-bit ones. One commenter who daily-drove IQ3 underscore XXS and IQ3 underscore S said IQ3 underscore S was noticeably better for coding. However, IQ3 underscore S needs about 55 gigabytes for its experts, and I only have 62 gigabytes total. That was too tight, so I settled on IQ3 underscore XXS. Also, the second shard of the model, which is the n-gram table, is the same file for all four sizes. Changing the size only changes the first shard.

I looked at some detailed posts on Reddit. The most detailed one for a 3090 described achieving 1,650 tokens per second for prompt reading and 38 to 61 tokens per second for generation, with no tool-call errors. The author had to rebuild Strata with specific tweaks and disable a fused feature to prevent crashes. I skipped all of that because those changes were for Unsloth quants and that person had 128 gigabytes of RAM. On the ISTA quants Strata ships by default, you don’t need them. The two things I did take from Reddit were the sampling values and a note that Strata maps the thinking level "high" to the model’s "xhigh," so you don’t need to worry about that mismatch.

For sampling, the Qwen model card gives two profiles. For thinking mode, which is the default, you use a temperature of 1.0, top p of 0.95, top k of 20, min p of 0, and a presence penalty of 0. For non-thinking mode, you use a temperature of 0.7, top p of 0.8, top k of 20, min p of 0, and a presence penalty of 1.5. I use thinking mode, and the Reddit benchmarkers recommend the same values.

Let’s move on to configuration. On a clean Ubuntu box, Strata’s setup script is one command. On my Pop OS box, I needed three fixes. First, the setup script wanted to install python3-venv using sudo. Since I was running it over SSH without a terminal, sudo couldn’t ask for a password. Strata supports an alternative tool called uv. I installed uv for my user and set an environment variable called STRATA UV equal to 1. Second, my version of CMake was too old. Pop OS 22.04 has version 3.22, but Strata needs 3.24 or newer. The setup script had already installed a newer CMake into its virtual environment, so I put that virtual environment’s bin directory first in my path. Third, there was no prebuilt engine binary available; the download link returned a 404 error. The setup script then compiled the engine for my GPU architecture using my CUDA toolkit, which worked without changes.

The download for the model weights is about 82 gigabytes. My download ran at 15 megabytes per second. I initially thought Hugging Face was slow, so I opened four extra connections to test that theory. Strata’s download speed dropped to half speed, and the total remained at 15 megabytes per second. It turned out my Wi-Fi was the bottleneck. I also lost a night of work because of a mistake with the process kill command. I used pkill with the pattern matching the setup script name, but it matched its own command line and killed the shell that was supposed to start the next download step. The fix is to use brackets in the pattern, like p-k-l-l dash f setup dot py. The brackets stop the pattern from matching itself.

There is a critical step regarding sampling that almost caught me out. The setup script writes a configuration file but does not include a sampling block. Strata’s documentation says that if there is no sampling block, requests without sampling keys decode greedily. This means a client that doesn’t send its own temperature will always get the single most likely token. I had to add the sampling block manually. I used the temperature of 1.0, top p of 0.95, top k of 20, and min p of 0.0 that we discussed earlier. I also added three other opt-in keys. First, expert profile save, which saves what the expert cache learned so a restart doesn’t start cold. Second, fit max tokens, which shortens an agent’s requested output size to fit the remaining context instead of throwing an error. Third, reasoning close retry, which catches a reply that ends inside its thinking process without giving an answer. Without this, the agent just stops. I also set a reasoning budget of 16,384 tokens. This forces the model to stop thinking and answer if it runs out of budget, which I added after two turns ran out of tokens mid-thought. Finally, I added aliases so the model appears under multiple names in the model list. Running the setup script again rewrites this file, so I keep these keys in a small script and run it after every setup to restore them, along with calibrated engine arguments and cache flags.

Another thing to note: the setup script turned KV streaming off by itself. It estimated that the model plus streaming would use 60 gigabytes, but I have 63, which was too close for comfort. So, the KV cache stays in VRAM, which leaves a bit less room for experts.

Calibration is the next step. The setup script tests a few engine settings over three rounds. It keeps a setting only if it beats the default by more than 3 percent. It took about 10 minutes. For the PCIe share, which controls how much off-GPU expert work is copied to the card versus computed on the CPU, the best setting was 0.2, achieving 99.6 tokens per second. Performance dropped hard after 0.75, down to 84 tokens per second at 1.0. This fits my PCIe 3.0 slot. The draft floor setting won its sweep but didn’t beat the defaults in the final head-to-head, so it stayed at 0.5. The kept settings were pool workers set to 4, adapt every set to 1, adapt swaps set to 80, and adapt decay set to 0.97, which achieved 105.4 tokens per second. These settings are saved per PC and model, but if you change the context size, the calibration doesn’t automatically come back. You have to carry those flags over by hand.

I moved to a 200,000-token context window. To do this, I reran the setup script with a new context size and a specific KV format. The k8v4 KV format stores keys as INT8 and values as 4-bit. This uses 23 percent less KV memory. At 128,000 tokens with standard int8 KV, I only had 461 megabytes of VRAM free after loading, and Strata printed a warning because it was below 512 megabytes. Below that, the driver can page GPU memory out to RAM. With the new 200,000-token setup using 4-bit values, I had 785 megabytes free. The expert cache slots went down from 9,746 to 9,227.

You should also check for other servers on your port. When I stopped my llama-server, my GPU monitoring tool still showed 20 gigabytes in use. A different llama-server had started 18 seconds earlier. It was a Qwen 36 model from months ago. It was running as a systemd user unit, enabled, set to restart on failure, and bound to port 8080. While the system server held the port, it failed and retried forever. Once the port was free, it snatched it up immediately. I had to disable that user unit. If you swap models often on one box, check the systemd user units too, not just the system ones.

I set up systemd services and a script to switch between models. Both servers need the whole GPU and port 8080, so only one runs at a time. I created a systemd service for Strata that conflicts with the llama-server service. The Strata service runs a script that acts as a symlink to the actual run command, making it easy to switch model sizes by just moving the symlink. I set memory lock limits to infinity because Strata pins tens of gigabytes of RAM for the GPU, and the default limit was only about 8 gigabytes. I also set a timeout of 120 seconds for stopping because releasing that pinned memory takes longer than a normal server shutdown.

On top of this, I have a small script in my local bin directory called llm-switch. Switching to Strata stops the 27B model, starts Strata, and waits for the health check. Switching to the 27B does the reverse. There is also an off option that frees the GPU and RAM, and running it with no arguments tells you which one is running. The script disables one unit, waits for the port to be free, enables the other, and polls the health endpoint. I added a sudoers rule to allow these specific systemctl commands without a password. Whichever model I switched to last starts at boot. Strata takes 35 to 45 seconds to come up, while the 27B takes about 15 seconds.

One gotcha: if your switch script prints a usage message that doesn’t match what you expect, you might have an old script shadowing the new one in your interactive shell. Use the type command with the dash a flag to see which one wins. I renamed the old one.

Next, connecting OpenCode through OmniRoute. OmniRoute already had a provider set up for my box. Strata accepts any model name, so routing worked without re-syncing the model list. I added the Strata API key to that connection. The llama-server ignores the key, so my old path kept working. In the OpenCode configuration, I defined the Strata model with a context limit of 204,800 and an output limit of 32,768. I enabled tool calling and reasoning. I set the reasoning effort to high by default, with variants for medium, low, and none. The none variant is nice for small edits because it answers immediately. I used a file reference for the API key so the key isn’t hard-coded in the config file.

OmniRoute had its own hidden context limit. A 130,000-token prompt failed with an error saying the input exceeded the context window of 128,000. I had to set a manual context override through OmniRoute’s API. After that, a 130,000-token prompt went through in 65 seconds, with 51.6 seconds spent reading the prompt. OmniRoute also has a readiness timeout. If the first response event takes too long, it gives up. The default is 80 seconds, with bumps for large requests. I had to increase the stream readiness timeout to 240 seconds and the max timeout to 420 seconds in the environment file and restart OmniRoute.

Finally, compaction settings. OpenCode compacts the conversation when it gets close to the context limit. The buffer defaults to 10 percent of the limit. At 204,800 context and 32,768 output, this meant compacting around 151,000 tokens. I tried setting a buffer of 4,096, which pushed the compaction to 182,900 tokens. I settled on a buffer of 16,384 in the global config, which compacts near 155,000 tokens. I’ll explain why I don’t squeeze out the last 30,000 tokens later.

Let’s look at the results. I ran the same script against both servers, streaming with 512 output tokens and random nonces to avoid caching. For a small prompt of about 925 tokens, the 27B model produced the first token in 1.2 seconds, while Strata took 2.0 seconds. For prompt reading, the 27B was faster at 1,166 tokens per second, compared to Strata’s 530. However, for generation, Strata was faster at 96 tokens per second versus the 27B’s 70.

For a 27,000-token prompt, Strata produced the first token in 11.5 seconds, beating the 27B’s 21 seconds. Strata read the prompt at 2,400 tokens per second, nearly double the 27B’s 1,332. Generation was 102 tokens per second for Strata versus 62 for the 27B.

For an 86,000-token prompt, the difference was even starker. Strata produced the first token in 32.2 seconds, while the 27B took 83.1 seconds. Strata read the prompt at 2,724 tokens per second, more than double the 27B’s 1,059. Generation was 101 tokens per second for Strata, while the 27B dropped to 49.

The 27B still wins on tiny prompts. What surprised me was the long-prompt performance. Strata’s own tables suggested it would be slow at reading, but past a few thousand tokens, it is about 2.5 times faster than llama dot cpp. Generation barely slows down as context grows for Strata, staying around 100 tokens per second even at 86,000 context. The 27B drops from 70 to 49. Since coding agents resend big prompts every turn, these long rows are where I spend my time. These are just speed numbers. I also tried an agent benchmark but stopped it because the 27B version was too slow.

I ran the probe again after moving to 200,000 context with 4-bit KV. On long prompts, the 200,000 context setup costs 5 to 8 percent performance compared to the 128,000 int8 setup. Generation is still 1.5 to 1.9 times faster than the 27B. There was an odd anomaly on the small 1,000-token prompt, where one run took 4.6 seconds and another took 9.4 seconds. My guess, which I haven’t confirmed, is that Strata was moving the previous conversation into the RAM cache while free RAM was low. Since small prompts aren’t where an agent spends most of its time, I left it.

Now, let’s talk about what changed after my first day of real use. My first session was a long code review with subagents. It involved 406 requests and 14.2 million prompt tokens. Only 35.5 percent were reused from cache. 308 requests reused nothing at all. This meant about 57 minutes of the session was spent just reading prompts. Strata normally keeps only one conversation cached at a time. My main session and a subagent took turns, so every time they switched, the prompt had to be read again from the beginning. This took 14 to 30 seconds each time. The fix is to enable a conversation cache with 6,144 megabytes and 4 slots. This parks up to four conversations in RAM. They don’t run in parallel, but they stay ready. After enabling this, 92.5 percent of tokens were reused. Zero-reuse requests dropped from 308 to 8. Prompt reading time dropped from 57 minutes to 12 minutes. A 68,000-token prompt now starts in 2 to 3 seconds instead of 30. In a later session, median time to first token was 8.3 seconds. The cost is up to 6 gigabytes of RAM.

Parallel subagents had another problem. They queued behind the server, which handles one request at a time, and OmniRoute stopped waiting. It logged 28 errors saying no model output within 110 seconds. Some errors happened at 130 seconds. Then, strangely, OmniRoute threw a 401 Unauthorized error saying there were no active credentials. Nothing was actually wrong with the credentials, but this fake error killed three subagents. That’s why I increased the readiness timeouts. However, the better advice is to run subagents one after another against a local single-request server.

Thinking budgets ran out twice. Two turns ended with a length error because the model reached the max tokens while still thinking, leaving no answer. This is why I set the reasoning budget token limit. This habit also broke the audio generation step for this blog, because Strata thinks by default and burns the token budget before answering. So now, that specific call sends reasoning effort none.

The real quality problem showed up near the top of the context window. In a 421-turn session, there were 13 tool-call errors. Seven were invalid JSON. Every one of those JSON errors happened at the highest contexts, right before compaction. They happened at 111,000 to 114,000 tokens, and later at 163,000 and 183,000 tokens. Below 110,000 tokens, there were almost no errors. The other six errors were empty write calls, edit calls where the search text didn’t match, and one background flag sent as a string instead of a boolean. The system always recovered, but at 160,000 tokens or higher, every retry costs a full turn. This is why I keep my compaction buffer at 16,000 tokens instead of squeezing out the last 30,000.

One compaction summary went wrong early on. At 115,000 tokens, the summary said "No development task has been stated yet." It mistakenly treated the system instructions as the objective and ignored what I had actually asked for. All six subsequent compactions got it right. Once, a stray thinking tag leaked into a visible answer.

The rest held up well all day. Generation stayed at 90 to 120 tokens per second, and prompt reading stayed around 2,500 tokens per second, with a 92 to 96 percent expert cache hit rate. There were no infinite loops, no repeat-token stops, no NaN guards, and no empty replies after thinking. Tool calls involving 16,000 to 19,000 tokens for big JSON writes came through intact.

This is what I’m watching for the rest of the week. I’m monitoring for loops, malformed tool calls past 110,000 tokens, bad compaction summaries, first-token time on big prompts, and RAM pressure now that the cache can take up to 6 gigabytes. I’m logging every issue. On the 21st, I will decide whether to keep Strata or switch back to the Qwen 27B model.
