Hey there! In this post, I’m diving into a fun project: bringing my Sony A6000 camera into the modern era. This camera is a gem, even though it was made way back in 2013 or 2014. I snagged it on eBay as a second-hand purchase, and now I want to give it a modern makeover by improving its data transfer capabilities, increasing resolution, and possibly even adding GPS functionality.

There are a few hurdles I’ve come across. The main challenge is finding a way to directly connect and communicate with the camera. It has Wi-Fi hotspot, which sounds great, but unfortunately, it enters a "dumb mode" when I try to use it for data transfer. It also limits a cell phone to no internet. Another option is the USB mass storage mode, but it turns out to be a bit problematic. Whenever pulling data too quickly, it just freezes up. Plus, it’s pretty sluggish with its USB 2.0 connection, which can take hours to download data.

Luckily, I’ve discovered the PC remote feature, which can be quite handy when the camera is connected to a computer. There’s this fantastic library called GPhoto2 that works wonders in this scenario, especially if I’m running Linux. It allows me to perform various actions on the camera remotely, like capturing images. However, I’m not keen on attaching a Raspberry Pi to my camera unless it’s absolutely necessary. Alternatively, I’m considering a microcontroller with an OTG port as a potential solution.

Join me on this hacking journey as I explore ways to modernize my Sony A6000 camera! By the way, Part 2 of this series has been published, so you can find the link on the blog post if you want to jump ahead. Let’s get started.

The first section is about getting data fast, and specifically, the hurdles we face. These files are large. Twenty-four point three megapixels averages around seven to ten megabytes per photo.

Here is the list of issues I had to solve. First, downloading the data from the disk is mandatory as the USB transfer rate is too slow. Using the SD card seems to be the best way. Second, the file names are really ugly. They have a format of DSC followed by four Xs and then a number. It iterates plus one, which is meaningless to understand. I adopted the format year, month, day, underscore, hour, minute, second using the image’s timestamp. While I could save as timestamp via the camera settings, I choose to opt out of that behavior, which I will explain later. Third, DSLR cameras can take multiple pictures in a second. Appending the image count to the end of that format, so year, month, day, underscore, hour, minute, second, underscore, and then the count. And fourth, offloading to external storage, using OneDrive since it’s available in the web, mobile, and desktop experiences.

I wrote a quick Python script to solve these problems. You can find the link to the script on the blog post. This script solves it in a three-part process: download, rename, and then transfer to a storage. Each step requires pauses for verification but could be altered in the future for more post-process work. My thought would be to use Darktable more frequently, but this works for most cases.

To show you what this looks like in practice, I ran the script, and here is the output I saw on my terminal. It first said, "Found Disk. Files 14. Press Enter to copy..." Then it copied from the DCIM folder to a temporary folder. After that, it said, "Copied 14. Press Enter to rename..." And then it listed out the renaming process, moving files like DSC08808.JPG to 20230612_151432.JPG, and DSC08809.JPG to 20230612_151436.JPG, continuing all the way through to DSC08821.JPG becoming 20230612_190600.JPG. Finally, it said, "Copied 14. Press Enter to move... Done."

After some pre-scanning and ARP Ping Scans, it initiated a SYN Stealth Scan. It discovered an open port 8080 TCP on the camera IP 192.168.122.1. It also discovered an open port 61000 TCP. Just the two services it needs to allow the mobile app to make its calls. Using their SDK, this works! I wrote a quick Python snippet. I imported the Camera and Actions from libsonyapi. I created a camera instance, got the camera info, printed the name and API version, and then executed the action to take a picture.

This will take the camera out of the app screen. The camera kind of goes into dumb mode. Only the basic modes can be used. I set it to "Intelligent Auto" to keep taking regular photos. After digging around, the post view image size could be changed to the **Original** file! Since taking a picture is the only way to get to that URL. Indeed, it gave the FULL path on disk! The URL was http://192.168.122.1:8080/postview/memory/1000/DCIM/100MSDCF/DSC08843.JPG.

Here is the quick script to capture and download. I imported requests, Camera, and Actions. I defined a function called capture_and_download. Inside, I created a Camera instance. I told it to set the PostviewImageSize to "Original". Then I executed the action to take a picture. I extracted the image URI from the response. I used requests to get the content of that URI. And finally, I opened a file named img.jpg in write binary mode and wrote the image data to it. If this is the main program, it runs the capture_and_download function.

Could I do some URL hacking to get other files? Yup! I took a photo manually then tried the updated URL. I now can download all the files by iterating backwards from the last known photo! When the bytes of the images end, it’s over. I’m sure Sony didn’t want this for a reason... likely it would kill the camera, so use it at your own risk!

Next up is Super High Resolution Images. Doubling the camera’s 24 megapixels output is possible by using a burst of pictures! It took a few days of hacking. Here is the process. First, take pictures with smart remote API. Four seem to be the max at ten seconds intervals. Second, read images into memory. Third, resize images by 200%. Fourth, align similar features in the images. Fifth, blend with transparency of 50%. And sixth, repeat three times since it would be the first two super images then last two super super images to one. So, twenty-four point three megapixels times two, times two equals ninety-seven point two megapixels! It looks more like a forty-eight point six megapixel version. You can find the super resolution code on GitHub via the link on my blog.

Here is a snippet of the Python code I used for this. I imported OpenCV and used imread to load two images. I set the interpolation method to LANCZOS4. I set the scale to 2. I resized both images by doubling their width and height using that interpolation. Then I called an align_images function on the upscaled images. Finally, I saved the result to a temporary JPG file.

Next section is GPS. A GPS module doesn’t exist for this camera. I’ve done a few proof of concepts but they have pros and cons. There are multiple ways to solve this. First, use your phone to generate a QR code then take a picture of it in the camera. It can be post-processed. Second, use something like Google Maps history to match images times with GPS location. Third, use hardware device like the Neo 6m hooked up to a Raspberry Pi or microcontroller to collect time and location, then post-process. And fourth, my favorite is a combination of methods. It’s to add a super small GPS device that was hooked to a Raspberry Pi Zero mounted on the camera. With a quick proof of concept, it worked well! Unfortunately, uploading files to the camera seems impossible. At least with all the options I’ve tried. The other major issue is something like a Raspberry Zero W 2 has a limit of 64GB of storage. So it should be offloaded quickly.

Here is the gear list for this part. First, the u-blox NEO-6M GPS module, which logs time and location for post-processing, available on Amazon. Second, a Super small GPS module, which is a tiny GPS for the Pi Zero build, also available on Amazon. You can find the links to these products on my blog.

Here is a quick Python script to collect GPS data off the GPS serial device. I imported serial and pynmea2. I opened the serial port COM4 at 9600 baud. I created an NMEA stream reader. In a while loop, I read lines from the serial port. If the first six characters were $GPRMC, I parsed the data using pynmea2. I extracted the latitude and longitude and printed them out.
