I was building a service that needed to call another internal API on behalf of a logged-in user. This is a standard issue where services need to talk to each other, specifically as that user. I had Authentik running already, so I went looking for RFC 8693 token exchange support. It turns out, it is not supported! Instead, what you get is JWT authentication. This is a legitimate machine-to-machine pattern, but it has a trust assumption baked in that is easy to miss until something goes wrong.

I built a demo repository that runs both approaches side by side. You can find the link on the blog post. It shows Keycloak with native RFC 8693, and Authentik with the JWT federation workaround, so you can see exactly where they diverge. There is also an image in the post that depicts city lights connected across a global network, symbolizing services passing identity tokens between each other.

Let’s look at the use case. Imagine a user logs into App A. App A wants to show how many todos this user has in App B. So, App A calls App B’s API for the todo count. This is a server-to-server call. But App B needs to know who the request is for.

App A cannot just forward the user's token because that token is scoped to App A. App B will reject it. You also cannot mint a new token yourself, because that defeats the whole point of having a trusted identity provider. You need the Identity Provider to issue a new token for App B, carrying the original user’s subject identifier.

Let’s look at Option A: Authentik.

Authentik does not implement RFC 8693. What it does offer is JWT authentication, which uses an RFC 7523 client assertion. This lets one service prove it is who it says it is using a signed JWT as the client assertion.

App A posts to the token endpoint using the client credentials grant type, with the user's access token as the assertion. Here is roughly what that looks like in code: you define parameters for the grant type, the client ID, the client assertion type as a JWT bearer, and then you pass the user’s access token as the client assertion. You also specify the scope, including an on-behalf-of-sub parameter.

There is one important note on that client assertion field. RFC 7523 normally expects a JWT signed by the client's own private key, not a user's access token. Authentik's federated provider feature accepts the user's access token here because it trusts the issuer. This is not standard RFC 7523 client authentication; it works, but it is Authentik-specific behavior.

Authentik verifies that App A's token comes from a trusted federated provider, and then it issues a new token with an audience of App B.

Here is the problem: the issued token’s subject is not the user. It is a service account, something like "ak-App-A-Provider-client_credentials." Authentik has no mechanism in this grant path to forward the original user's identity into the token.

So, App A has to pass the user identity separately when calling App B. In the code, you see App A making a fetch request to App B’s API. It includes the exchanged token in the Authorization header, but it also includes a custom header called "X-User-Sub" with the user's subject ID.

App B trusts that header because the bearer token proves the caller is App A's server. But that trust is implicit, not cryptographic. A bug or compromise in App A could cause App B to return another user's data. The user identity is not bound to the token; it is just a header that anyone with App A's credentials could fabricate.

The concrete risk is this: if App A is ever compromised—maybe through a dependency vulnerability, a leaked secret, or a misconfigured environment variable—an attacker can call App B as any user in the system. The Identity Provider has no knowledge of who the request is "for." App A decides that, and App B trusts it. With the Keycloak path, the Identity Provider is the one asserting the user's identity in the token. App A cannot forge that claim even if it is fully compromised.

There is a demo image in the post showing this with Authentik. It shows the login, the SSO into App B, and the todo count appearing in App A, with an orange badge indicating it is a workaround.

Now, let’s look at Option B: Keycloak.

Keycloak has supported RFC 8693 token exchange natively since version 12. The grant type is specifically for token exchange.

App A posts the user's access token as the subject token and asks for a new one scoped to App B. In the code, you set the grant type to token-exchange, include the client ID and secret, pass the access token as the subject token, specify the subject token type, and set the audience to App B.

Keycloak validates the subject token, checks the exchange policy, and issues a new token with three key things:
First, the audience is set to App B.
Second, the subject is the original user’s subject ID. This is the real user, not a service account.
Third, the authorized party claim is set to App A, recording who performed the exchange.

With the user’s subject already in the token, App A calls App B with no extra header. In the code, you just see the Authorization header with the exchanged token. There is no X-User-Sub header needed because the subject is in the token itself.

App B validates the token's audience and reads the subject directly from it. No extra header. No implicit trust. The user identity is cryptographically bound.

There is another demo image showing this with Keycloak. It shows the login, the SSO into App B, and the todo count appearing in App A, but this time with a green badge indicating it is RFC 8693 compliant.

Let’s talk about what happens on the App B side.

App B enforces a strict audience check on every service-to-service call. It verifies the JWT against the JWKS, checking that the issuer is correct and that the audience matches App B. This rejects any token not scoped to App B.

Then, the API handler branches based on the identity provider type to get the user identity from the right place. If it is Keycloak, it gets the user identity directly from the validated token’s subject. If it is Authentik, it gets the user identity from the X-User-Sub header, trusting it only because the audience check passed.

This is where the security models visibly diverge. With Keycloak, identity comes from the token. With Authentik, identity comes from a header App A set.

Here is the key difference, visualized in a sequence diagram in the post.

In the Authentik path, the user logs in, gets a token for App A. Then, when requesting data from App B, App A asks the Identity Provider for a client credentials token using the user token as an assertion. The Identity Provider issues a machine-to-machine token with a service account subject. App A then sends that token to App B, along with the X-User-Sub header. App B trusts the header because App A is authenticated.

In the Keycloak path, the user logs in, gets a token for App A. Then, when requesting data from App B, App A asks the Identity Provider for a token exchange, passing the user token and specifying App B as the audience. The Identity Provider validates the delegation policy and issues a delegated token with the user’s subject and App A as the authorized party. App A sends only that token to App B. App B verifies the subject and authorized party from the token itself.

There is also a comparison table in the post.
For Authentik, the grant type is client credentials with RFC 7523 client assertion. It does not support RFC 8693. The identity chain is broken because it requires a manual X-User-Sub header.
For Keycloak, the grant type is token exchange per RFC 8693. It does support RFC 8693. The identity chain is preserved because both the subject and the authorized party are in the issued token.

So, with Authentik, you are trusting App A to tell the truth about who the user is. With Keycloak, the Identity Provider is the one asserting it, and App B can verify that independently.

If you want to run this yourself, here is how.

Clone the repository. You can find the link on the blog post. Then copy the example environment file to a new .env file.

To run the Keycloak stack, use Docker Compose with the specific Keycloak configuration file.

Before you start, add these entries to your /etc/hosts file:
First, map the hostname "authentik" to 127.0.0.1.
Second, map the hostname "keycloak" to 127.0.0.1.
Both stacks use port 9000 for the Identity Provider.

Wait about thirty seconds for Keycloak to initialize. Then:
App A is available at localhost port 3993. This is where you log in.
App B is available at localhost port 3994. This is where you add todos.
The Keycloak admin console is available at keycloak port 9090.

Use the credentials "demo" and "changeme" for app login, and "admin" and "changeme" for Keycloak.

Log in to App A, open App B in a new tab so SSO kicks in automatically, add a few todos, and go back to App A. The todo count shows up. There is a Token Exchange Info card on App A that shows which method was used and whether it is RFC compliant.

Here are the takeaways:

First, Keycloak just works for RFC 8693. The setup script in the repository automates the token exchange permission policy so you can see the full flow without manual admin steps.

Second, Authentik's JWT authentication is a legitimate machine-to-machine pattern. But when the goal is passing a user's identity downstream, the subject in the issued token is a service account, not the user. That gap is what forces the X-User-Sub header and shifts the trust to App A.

Third, the authorized party claim matters. In the Keycloak response, the authorized party claim records which service performed the exchange. App B can use that to enforce policies about which services are allowed to act on behalf of users.

Fourth, audience validation is not optional. Both options enforce strict audience checking on App B. If you skip it, any token from the same Identity Provider gets through, which defeats the whole point.

For references, you can look up RFC 8693 for OAuth 2.0 Token Exchange, RFC 7523 for the JWT Profile for Client Authentication, the Keycloak Token Exchange documentation, the Authentik JWT Authentication documentation, and the demo repository itself. You can find all these links on the blog post.
