**Title: Building a Custom HTTP Proxy in Rust for Mixed-OS Workflows**

**Introduction**

To give you the long, short version: I built a proxy written in Rust. My goal was twofold. First, I wanted to keep my internet traffic private. Second, I needed remote access to my home devices. The result is lightweight, requires no dedicated app, and works on any device that can be configured to point to a proxy.

I want to walk you through the privacy benefits, how I use it for local services, and why I still use this setup even though I have access to a full-tunnel corporate VPN.

**The Problem**

This all started because I wanted to switch to a minimalist operating system. Specifically, I wanted Linux. But there was a catch-22. My job didn’t support Linux. At the time, it didn't even support macOS. I had to use Windows because of the corporate VPN and a bunch of strict security policies. I couldn’t just switch my computer over and be done with it. So, I had to get creative.

I wanted Linux as my daily driver. Work required Windows for the VPN and certain specific tools. I tried using WSL2—Windows Subsystem for Linux—which is okay, but honestly, it felt like fighting the operating system half the time. Handling USB devices, running GUI applications, and doing bulk file operations were all slow or just plain broken. They didn't work the way I expected.

I needed a way to run Linux full-time on my personal machine, but still access my work’s Windows environment seamlessly.

**First Attempts**

I tried using Squid proxy first. It worked… mostly. But I ran into random issues from time to time that I couldn't quite figure out. Then, I wrote a script in Python to handle the proxying. That was better, but it felt hacky.

I knew I could do better. And, honestly, I wanted to learn Rust anyway.

**The Rust Proxy**

So, I built a transparent HTTP and HTTPS forward proxy in Rust. It’s nothing fancy, but it solves my specific problem perfectly.

Here is what it does:
First, it supports HTTP and HTTPS proxying via CONNECT tunneling.
Second, it has SSL/TLS error detection with helpful diagnostics. This is crucial because corporate certificates are a pain to deal with.
Third, it integrates with the Windows firewall and automatically creates rules for the proxy port.
Fourth, it generates cross-platform binaries for Windows, Linux, and macOS.
And fifth, it allows you to configure the host, port, and logging levels.

I did use an AI coding assistant to help me build this since I didn’t have a lot of experience with Rust at the time.

Why did I choose Rust? The performance is solid. The async architecture, powered by Tokio, handles plenty of concurrent connections without causing any problems.

If you want to see how to get it running, the process is simple. You download the latest release binary for your platform. Then, you run it with a specific host address and port. For example, I run it on all interfaces at port 3129. Once that’s running, you just point your system or app proxy settings to that host and port. That’s it.

**PopOS Setup: The Real Work**

The proxy was actually the easy part. Getting PopOS to play nice with my work setup? That took some doing.

**Docker Install**

Docker doesn’t come pre-installed on PopOS, so I have to install it manually. Here is the general flow of what I do. First, I update my system packages. Second, I install the prerequisites like curl and GPG. Third, I add Docker’s official GPG key to my system. Fourth, I add the Docker repository to my sources list. Fifth, I update the package list again and install the actual Docker engine, the CLI, and the Compose plugin. Sixth, I start the Docker service and enable it to run on boot. Seventh, I add my user account to the Docker group so I don’t have to use sudo for every command. And finally, I verify the installation by checking the versions. After that, you need to log out and back in to apply the group changes.

**GitHub Account Switching**

I have both a personal GitHub account and a work account. To switch between them, I use the GitHub CLI. If I’m working on work stuff, I switch to my work user. If I’m doing personal projects, I switch to my personal user. It would be nice if there was a simpler alias for this, but for now, this works well enough.

**Flatpak X11 Fallback**

Some Flatpak apps don’t work well with Wayland, the modern display server. I found that VSCodium, specifically, had issues. To fix this, I force it to use X11 by setting a specific override for that application’s sandbox environment. This forces the graphical interface to render through the older, more compatible protocol.

**.NET and Node.js**

For .NET, I keep a local install but link it to the system path so I can call the dotnet command from anywhere without worrying about paths. For Node.js, I use NVM, which is a version manager. I install it using the standard install script from GitHub. This allows me to switch between different versions of Node as needed.

**PopOS Fun Window Issues**

PopOS isn’t perfect. Here are some of the specific fixes I had to make to get it right.

**Gnome Tweaks**
There are a few shortcuts and tweaks that help. You can adjust services that start up automatically by running a specific session properties command. You can change workspaces quickly using a combination of the Super key, Control, and Up or Down arrows. And if things get stuck, you can restart the Gnome shell interface by pressing Alt and F2, typing "r", and hitting enter. It’s a bit like a soft reboot for the desktop.

**Bluetooth**
I actually ditched my old Bluetooth adapter because it caused issues with PopOS all the time. To save power and avoid conflicts, I disable the internal adapter when I’m not using it. I use the HCI config tool to list devices and then bring the interface down.

**Audio Power Saving**
This was a common fix for audio glitches. The sound card driver has a power-saving mode that can cause dropouts. You can disable this temporarily by writing a zero to a specific system file. Or, for a permanent fix, you create a configuration file in the modprobe directory that tells the sound driver to never enter power-save mode.

**Wireplumber Suspend**
There’s a service called Wireplumber that manages audio sessions. Sometimes it suspends too aggressively. I edited its configuration file to set the suspend time to zero, preventing unwanted suspensions. Then, I restarted the PipeWire service to apply the changes.

**VSCodium GPU**
If VSCodium is crashing for you, try launching it with the GPU disabled. It’s a simple flag that tells the app not to use hardware acceleration for rendering.

**Chromium Proxy Setup**

This is the part that actually makes everything usable. I run different work apps through different proxies. Here is how I launch Chromium with specific proxy settings.

I use a Flatpak instance of Chromium. I launch it with a command that specifies the profile directory and, crucially, the proxy server address. I point it to my local IP address and port 3129 for both HTTP and HTTPS traffic. Since I’m dealing with corporate certificates, I also add a flag to ignore certificate errors. This is useful for internal tools that might have self-signed or intermediate certs that the browser doesn’t trust.

I have multiple of these setups for different work contexts. It’s not elegant, but it works.

**Flatpak Sandbox Chrome Alias**

For convenience, I set up an alias. When I type this alias in my terminal, it launches Chromium in a sandboxed Flatpak instance with the proxy already configured and certificate errors ignored. This keeps the proxy settings isolated from my regular browser installation and ensures the sandboxed instance respects the corporate certificate chain without messing up my personal browsing profile.

**The Router Setup**

I use a travel router to connect my Linux machine to the work Windows machine via Ethernet. It’s basically a home lab, but for work. The router runs Wi-Fi 7, which is nice because my work laptops are from 2019 and don’t support that newer standard. Since I’m proxying all traffic through the work laptop, this gives me low latency and fast file transfers.

**15 Months In**

It’s been over a year now. Here is where I’m at:
First, I’m running PopOS full time on my personal machine.
Second, my work machine is also running PopOS Cosmic.
Third, the Rust proxy handles all my traffic routing to a Windows PC that I keep around for legacy tools.
Fourth, I use the proxy to split internet traffic. Work stuff goes through the corporate VPN, and everything else goes direct.
And fifth, I no longer use OneDrive on my desktop. I use the web version, Git, or my personal knowledge management system instead.

Would I do anything differently? Maybe I wouldn't have spent so much time optimizing Windows when all work systems deploy to Linux containers in production anyway. The ecosystem lock-in is real. Once you’re in, it’s hard to get out. But with some creativity and a little custom code, you can make mixed-OS workflows work for you.

**Work VPN Conflicts**

I use a full-tunnel work VPN, which can be problematic for development. Tools like NPM, NuGet, and pip can be extremely slow because all traffic is forced through the corporate network. SSL certificates can also be an issue. With a full VPN, an intermediate certificate is installed and becomes part of the chain. I’m not a TLS expert, but it can cause headaches.

Companies may not even like proxies installed on the PC or allow them in general use. Route tables and routing traffic become interesting puzzles. I use a proxy in two different ways depending on the use case. I’ve been using an HTTPS proxy for over a year. It solved a few major issues for me. In the age of WireGuard and Tailscale, you might wonder why I still use it. But for this specific corporate environment, it makes the most sense.

**Conclusion**

So, what are the takeaways?

First, keep it simple. A single, lightweight proxy can solve a lot of headaches without the bloat of a full VPN client.

Second, don’t over-optimize. I spent a lot of time tweaking Windows, but the real win was on the Linux side. Focus on the part that actually matters to you.

Third, document early. The notes you keep for yourself become the next blog post. I’m still adding to my setup notes, and that’s why this is a living document.

And fourth, stay curious. The tech landscape changes fast. What worked for me last year might be obsolete next year, so keep experimenting.

Bottom line: if you’re juggling a corporate VPN and a personal workflow, a transparent forward proxy is a surprisingly powerful tool. It keeps your traffic private, gives you remote access to home services, and lets you sidestep the slowdowns of a full-tunnel VPN. Give it a shot and see how it changes your day-to-day dev life.
