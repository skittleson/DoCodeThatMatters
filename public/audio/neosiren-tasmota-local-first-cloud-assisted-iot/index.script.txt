So, this guide is about flashing a NEO Coolcam Siren, which also has a temperature and humidity multisensor built in, with Tasmota. The goal here is to get a local-network-first setup running.

Let’s start by looking at the components you will need. First, you obviously need the NEO Coolcam Siren Multisensor itself; that is the device we are modifying. Second, you will need a serial-to-USB adapter. You can find this on Amazon if you need to buy one. Its purpose is to connect the ESP8266 chip inside the device to your PC so you can actually flash it.

Now, for the wiring guide. This is a condensed version of the process. If you want a full getting-started guide, you can find that in the official Tasmota documentation online. To flash this specific device, you will need to solder onto the PCB. There is a plate on the back that needs to be rotated to expose the battery holder. Once that is open, go ahead and remove the three screws.

The tricky part is making all the connections via soldering. Remember, you need that serial-to-USB adapter. Here is how the connections should look between the device and the flasher:
First, connect GPIO0 on the Neo Coolcam to Ground, or GND, on the flasher.
Second, connect GND on the Neo Coolcam to GND on the flasher.
Third, connect TX on the Neo Coolcam to RX on the flasher.
Fourth, connect RX on the Neo Coolcam to TX on the flasher.
And finally, connect 3.3 volts on the Neo Coolcam to 3.3 volts on the flasher.

There is an image in the post showing the soldering points marked up on the device, and another one showing the finalized soldering job where everything is wired to the flasher.

Next, let’s talk about flashing. First, you need to install esptool. You can do this quickly using PyPi. In your terminal, just run the command: pip install esptool.

Once that is installed, it is time to flash. Change the port to whatever COM port or serial port your device is on, and then run the following command in the terminal. This works whether you are on a Mac, Linux, or Windows when using PyPi. The command is: esptool, then dash-dash-port, then your port number like COM3, then write_flash, then dash-f-s 1MB, then dash-f-m dout, then 0x0, and finally the filename tasmota-sensors.bin.

There is an image in the post showing what this looks like in the terminal while it is flashing. If you prefer a graphical interface instead of the command line, you can use a GUI tool called Tasmotizer.

After flashing, you need to connect to the access point that the device creates to configure its default WiFi so it connects to your local network.

Now, for configuration. In the "Configure Other" section of the Tasmota web interface, you need to apply a template. The specific template for this Neo Coolcam can be found on Blakadder’s templates page. If you copy and paste that template in, it will set up the GPIOs correctly.

Next, there are some specific Tasmota console commands you should run to configure the sensor behavior. Let’s go through them one by one.
First, run: Backlog SetOption65 1; SetOption66 1; Module 54. This enables fast power cycle and registers the device as a Tuya module with module ID 54.
Second, run: TuyaMCU 11,104. This maps the alarm siren and LED to a toggle switch.
Third, run: TuyaMCU 71,105. This maps the indoor temperature reading.
Fourth, run: TuyaMCU 73,106. This maps the indoor humidity reading.
Fifth, run: TempRes 1. This sets the temperature resolution so that instead of seeing a value like 291, you will see 29.1 degrees.
Sixth, run: TuyaSend2 113,0. This disables the built-in temperature alarm, as you want to handle that logic with a rule instead.
And seventh, run: TuyaSend2 114,0. This disables the built-in humidity alarm for the same reason.

All of this assumes you have MQTT configured. The temperature and humidity data will not show up in the UI unless MQTT is set up. If you ever want to undo that specific setting, you can use SetOption66 0. It is also optional but good practice to ensure the dpId states are set by running TuyaSend0.

Once everything is hooked up, the data will be polled and reported every so often. However, there is a caveat: it does not always send both temperature and humidity; sometimes one might be missing. We have to account for that later in our logic.

In the post, there is a log snippet that shows what the MQTT message looks like when it arrives. It shows a time stamp and the TuyaSNS object containing the Temperature and Humidity values.

There is also a screenshot of the final result in the Tasmota Web UI, showing the Tuya temperature, humidity, and the siren/LED power toggle all working locally.

I have also considered using rules to catch the Tuya event and then publish the MQTT message within that rule, but let’s look at NodeRed next.

For NodeRed and other smart logic: First, set up an MQTT node. You need to subscribe to the topic tele/tasmota, followed by the ID of your device, slash SENSOR. You can find the correct ID on the Tasmota Information screen under "MQTT Full Topic."

Next, add a function node. This node needs to handle cases where temperature and/or humidity are undefined. It is also optional to add metadata such as a measurement name for use in Graphana.

The code inside that function node does a few things. It sets a measurement variable to 'siren-tv'. Then, it tries to parse the JSON payload. If the TuyaSNS object exists, it initializes a new payload object. It checks if there is a Temperature value and copies it over. It also checks for a Humidity value; if it exists, it multiplies that humidity value by 10 before copying it to the new payload. If anything goes wrong during this parsing, it logs an error saying "unable to get temp and humidity" and stops. Finally, it returns the message.

To turn on the siren remotely, you can send either "ON" or "OFF" to the MQTT topic cmnd/tasmota, followed by your device ID, slash POWER. When you do this, a return MQTT message will be sent back with the status at stat/tasmota, your device ID, slash POWER.

For further reading, you can check out the Blakadder templates page, the Tasmota TuyaMCU documentation, or a gist shared by Patrickdk77 on GitHub for more details on these configurations.
